# 工程科研工作台 · 定位与功能分层

> 依据：2026-10-09 对当前分支（`feature/slim-workbench-v261009`）代码与 `Workspace/` 数据的实测。
> 配套文档：[docs/REFACTOR_PLAN.md](REFACTOR_PLAN.md)（精简与插件化实施方案）。
> 本文回答三个问题：**这个工具是干什么的**、**哪些功能是核心**、**哪些应该是插件**。

---

## 0. 一句话定位

> **单人、本地优先的科研知识与文献整理平台**：把研究过程中产生的笔记 / 灵感 / 日志 / 实验 / 总结 / 里程碑 / 文献，沉淀成可检索、可互链、可汇总的 Markdown 知识库；在同一界面里完成**文献梳理与阅读**、**数据与报告留档**、**AI 辅助整理**。

Markdown + frontmatter 是唯一事实来源，SQLite 索引是可重建派生物；除显式调用外部服务（LLM / RSS / 天气）外，数据不出本机。

**明确不做的三件事**（边界，用于挡掉功能蔓延）：

| 不做 | 原因 |
| --- | --- |
| 多用户协作 / 权限 / 云同步编辑 | 单用户本地优先；协作靠 Syncthing 同步 `Workspace/` 即可 |
| 实验数据采集与分析系统（LIMS / ELN） | 不做采集、不做统计与绘图引擎；分析交给 Python/R 等外部工具 |
| 文献管理器替代品（Zotero / EndNote） | 不做云端文献库、不做 Word 引用插入 |

## 2. 功能分层

分层只有**两类机制**：**核心**写死在代码里、始终可用；**其余一切都是插件**（走同一套 manifest / 注册表 / 隔离机制）。插件再按两个轴分档：

| 档 | 谁维护 | 是否随包 | 默认状态 | 名字 |
| --- | --- | --- | --- | --- |
| 官方插件 | 本项目 | 随包发布 | **默认开**（设置里可关） | **附属功能** |
| 可选插件 | 本项目或第三方 | 不随包 / 按需安装 | **默认关** | **插件** |

> **「附属功能本质上也是插件」**：它不是一个特权层，只是「由内核作者维护、默认帮你打开」的那一档。因此 —— 附属功能必须遵守与插件完全相同的隔离不变量（REFACTOR_PLAN §6.4），核心也必须能在**所有附属与插件全部关闭**时完整跑通（§2.1 的运行不变量）。

### 2.1 核心功能（Core：零插件即可跑完整闭环）

| # | 核心功能 | 为什么是核心 | 现有实现 |
| --- | --- | --- | --- |
| C1 | **条目与知识模型**：7 类条目 CRUD、命名/字段契约、状态机、回收站、原子写 | 直接读写科研数据结构本身 | `store.py`(1190 行)、`kb_naming.py`、`workspace.py` |
| C2 | **组织**：项目、待办、科研活动日志 | 数据的一致性载体（归属、留痕） | `projects.py`、`todos.py`、`activity.py` |
| C3 | **检索与汇总**：派生索引 + 中文 FTS + 关系解析（wikilink/typed）+ 全局搜索 + 项目/阶段汇总 + 导出（Markdown 知识包 / BibTeX） | 「梳理与汇总」的必经环节 | `perf_index_*`、`indexer.py`、`store.export_bibtex`、`/api/graph/bundle` |
| C4 | **界面壳**：单页导航 + 列表/详情/编辑器 + Markdown 预览 | 一切功能的入口 | `web/index.html`、`app.js`、`styles.css` |
| C5 | **文献梳理**：文献条目 + PDF 附件登记 + 阅读状态 + 元数据补全 + BibTeX 导入导出 + 与知识条目互链 | 你的用途 ②，且已重度使用（67 条 / 56 篇） | `literature.py`(830 行)、`library.json` |
| C6 | **文献阅读（基础）**：PDF 打开/翻页/缩放/跳页 + 划词高亮批注 + 文献笔记 | 用途 ② 明确要求「在该平台完成阅读」 | `web/literature.js` + `web/vendor/pdfjs`、`/api/literature/<id>/pdf` |
| C7 | **AI 基础**：对话（SSE 流式）+ 6 个工具（检索/读取/建档/更新/文献上下文/文献笔记）+ 页面上下文注入 + 草稿确认流 | 用途 ③，且是知识沉淀的主要生产力 | `agent.py`(1004 行)、`agent_tools.py`(420 行) |
| C8 | **数据留档（最小）**：实验条目承载「配置与参数 / 数据与口径 / 结果 / 留档路径」，数据文件放 `Projects/<项目>/{Data,Results,Figures}` 并由条目引用 | 用途 ① 的「数据」底线：**登记与关联，不做分析** | `experiment` kind + 项目目录骨架（当前全空） |

**核心的运行不变量**：这 8 项全部可用时，即使一个插件都没装，平台依然能「录入 → 组织 → 检索 → 汇总导出」跑通，且数据完整。

### 2.3 可添加功能（可选插件：默认关、不随包、可自由增删）

判定：与「数据结构本身」无关，或纯展示/外部集成；删掉后核心闭环与数据完整性**都不受影响**。与附属功能**同机制、同等隔离要求**，唯一区别是默认关、需自行安装。

**A. 已有实现、应下沉为插件的**

| 插件 | 现状 | 备注 |
| --- | --- | --- |
| 语义检索 RAG | 完整实现在 `feature/rag-v261009`（已推送 origin），内核里已无代码 | 你已判定「非必要、体量大」；独立进程 + 92 MB 权重 + 69 MB 向量库 |

**B. 建议新增（由你的三条用途倒推出来的缺口）**

| 插件 | 解决什么 | 优先级 |
| --- | --- | --- |
| **数据视图**（指标表 / 曲线 / 数据集清单） | 用途 ① 的短板：把指标与图从正文里拿出来，成为可比较的表 | 高 |
| **报告导出**（DOCX / PDF / PPT） | 用途 ① 的"报告"：阶段汇总 / 项目条目 → 正式交付文档 | 高 |
| 文献库同步（Zotero / BibTeX 双向） | 用途 ② 的"梳理"与外部管理器互通 | 中 |
| 定时备份 / 快照（PDF 310 MB + 索引 117 MB） | 数据安全 | 中 |
| Obsidian / 本地目录双向同步 | 与其他笔记工具共存 | 中 |
| 统计与绘图桥（Python/R） | 真正的数据分析——**明确不进核心** | 低 |
| 日历 / 提醒（里程碑 due） | 时间管理 | 低 |

### 2.4 判定规则（以后新功能该放哪层）

1. **直接读写科研数据结构？**（条目 / 项目 / 待办 / 活动 / 索引 / 关系）→ 否则不进核心；
2. **去掉它，数据会失去一致性或不可恢复？**（校验、原子写、回收站、导出）→ 否则不进核心；
3. **是「录入 → 组织 → 检索 → 汇总/导出」闭环的必经环节？** → 否则不进核心。
4. 补充：**改变数据模型（新增 kind / 新字段）的功能**只能通过契约扩展机制接入，不得让核心为某个插件特判。

三条都不满足 → 就不是核心，**一律做成插件**；再按两个轴分档：属科研主线、官方维护、建议随包 → **附属（默认开）**；与科研数据无强耦合，或第三方/实验性 → **插件（默认关）**。
